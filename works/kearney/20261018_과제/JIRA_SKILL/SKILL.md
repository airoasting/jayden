# JIRA 티켓 작성 (기획자 → 개발자, MX 프로젝트)

기획자의 자유 형식 텍스트로 JIRA 티켓의 **제목과 본문**을 만든다. 독자는 개발자이고, 기획자·디자이너도 읽는다.
제품은 **MX MAP**(사내 마케팅 성과 분석 데스크톱 웹 대시보드)이다. 화면은 LNB(좌측 메뉴), GNB(상단 바), 필터 영역(기간, 법인·지역, Channel, Product), Metric Card(KPI 카드), 차트, 상세 성과 테이블, Excel/PDF 다운로드, Chatbot 패널, Admin으로 이루어진다.
**작성 전에 같은 폴더의 `examples.md`에서 입력과 가장 비슷한 예시를 읽고 형식·길이를 맞춘다.**

## 0. 원칙

1. **지어내지 않는다.** 입력에 없는 메뉴명·수치(화면 폭 px, 지표 값 포함)·문구·산식·시안 상태는 쓰지 않는다. 판단이 들어간 문장에는 `(제안)`을 붙인다.
2. **티켓 1건 = 요청 1개.**
3. **짧게.** 해당되는 블록만 쓴다. 값이 "없음"인 줄은 쓰지 않는다. 같은 정보(링크, 적용 범위, 0건 화면 등)는 한 곳에만 쓴다. 목표: 3줄 입력 → 본문 약 20줄.
4. **팀 말투와 쉬운 말.** 합니다체, 요청은 "~ 부탁드립니다", 검토 요청은 "확인 후 댓글 부탁드립니다". 메뉴·지표명은 화면의 영문 그대로 쓰고, 용어는 처음 나올 때 괄호로 푼다.

**표시 범례** (본문에는 이 세 가지만 쓴다)

| 표시 | 뜻 | 누가 처리 |
|---|---|---|
| `[확인 필요: 항목]` | 입력에 없어 비워 둔 값 (제목에서는 `[확인 필요]`) | 확인 질문에 답하거나 개발 중 협의 |
| `(제안)` | Claude가 판단해 넣은 내용 | 기획자가 승인하거나 지움 |
| `(확정 후 채움)` | 미확정 값 때문에 아직 판정할 수 없는 검증 항목 | 값이 정해지면 채움 |

**용어** (처음 나올 때 괄호로)
운영계(PROD, 실제 사용자가 쓰는 서버) · 배포(수정한 내용을 서비스에 반영) · 재현(문제를 다시 일으켜 보는 것) · 공수(작업에 드는 시간) · API(화면 뒤에서 데이터를 주고받는 통로) · 퍼블리싱(화면 마크업·스타일 수정) · 컴포넌트(공통 버튼·입력칸) · 프레임(피그마 안의 특정 화면, 링크의 node-id) · 법인(Subs, 해외 법인) · E/R(Engagement Rate) · YoY/MoM(전년/전월 대비) · VOC(사용자 의견·문의). "회귀 확인"은 쓰지 않고 "기존처럼 ~된다"로 쓴다.

## 1. 절차

**1-1. (선택) 기존 티켓 참고 — 읽기 전용**
Atlassian/JIRA 커넥터 도구가 있을 때만 한다. 사용자는 신경 쓰지 않아도 된다.
- **검색·조회만 한다. 티켓 생성·수정·코멘트·상태 변경·담당자 변경은 절대 하지 않는다**(사용자 지시). 결과는 텍스트로만 출력한다.
- MX 프로젝트(kearney-rockplace.atlassian.net, 키 `MX`) 최근 티켓 5~10개에서 **메뉴·탭 이름, 축약어, 용어**만 맞춘다. 내용은 옮기지 않는다.
- 같은 내용의 티켓이 있으면 비고에 `관련 티켓: MX-123`. 도구가 없거나 실패하면 조용히 건너뛴다.

**1-2. 입력 문장 분류** — 메모·슬랙·회의록 모두 문장마다 나눈다. 2장 판단 순서와 같은 기준이다.

| 문장 | 예 | 처리 |
|---|---|---|
| 확정·사실 | "기본은 전체 선택", 당사자가 확인한 재현 조건 | 반영 |
| 요청자 본인의 희망 표현 | 기획자가 쓴 "~있으면 좋겠어요" | 요청으로 반영 |
| 기획자가 전달한 법인·다른 팀 요청 | "미국법인이 ~해 달래요" | 티켓 작성. 배경에 요청 주체 기록 + [필수·기획] "진행이 확정됐나요?" (모르면: 검토 요청으로 등록) |
| 회의 참석자가 직접 낸 의견 | "법인 담당자: ~면 좋겠다는 의견" | 티켓화하지 않음 |
| 개발자의 원인 추정 | "배치 캐시라 그럴 수도" | 비고 `개발 확인:`에 "(개발 의견, 미확인)"으로. 사실로 쓰지 않는다 |
| 미결정 (할지 말지 자체가 미정, 기획·디자인이 결정) | "다음 회의 때 결정" | 티켓화하지 않음 |
| 개발 판단으로 결정 | "공수 보고 결정", "~하고 싶은데 되나?" | **검토 요청** |
| 의심되지만 확인 안 된 문제 | "??", "~인 듯", "~일 수도" | **검토 요청(원인 확인)**. 보안·권한·수치 신뢰성 의심이면 비고에 긴급. **절대 빼지 않는다** |
| 할 일은 정해졌고 세부만 미정 | "카드 정리 필요, KPI 위주로" | 해당 종류로 작성 + 세부는 [확인 필요] |
| 개발 외 할 일 | 시안 작업, 일정 공유 | 티켓화하지 않음. 개발 티켓의 선행 조건이면 그 티켓 비고에도 |

"티켓화하지 않음"은 출력 끝 **티켓화하지 않은 항목**에 한 줄씩 남긴다.

**1-3. 분리** — 위치·종류가 다르거나 따로 완료될 수 있으면 별도 티켓. 화면·Excel·PDF처럼 같은 데이터를 보여 주는 곳은 한 티켓의 **적용 범위**로 묶는다. 티켓끼리 관계는 비고에 `「제목」 티켓과 함께 배포`.

**1-4.** 종류(2장) → 제목(3장) → 본문(4·5장) → 질문(6장) → 자체 점검(8장) → 출력(7장).

## 2. 이슈 유형 (정확히 1개, JIRA '이슈 유형' 칸에 그대로 고른다)

| 이슈 유형 | JIRA 공식 설명 | 이렇게 판단 |
|---|---|---|
| 오류 수정 | 기능 혹은 디자인 오류 수정 요청 | 이미 정해진 동작(기획서·시안·기존 동작)과 다름. 툴팁·문구가 의도와 다른 것 포함 |
| 검토 요청 | 오류 혹은 로직 관련 검토 요청 | 개발자의 원인 확인·로직 설명·가능 여부·공수 답변이 결과물 |
| 기능 개선 | 기존에 있는 기능의 고도화 혹은 기능 수정 요청 | 있는 화면·기능을 바꾸거나 요소 추가 |
| 신규 기능 | 기존에 없던 새로운 기능 및 기획에 대한 요청 | 없는 메뉴·탭·독립 흐름을 새로 만듦 |

**판단 순서** (먼저 걸리는 것)
0. **두 곳의 값이 다르거나 기대와 다르다는 것이 확인됐으면 오류 수정**이다("어느 게 맞는지 모르겠다", "원인 확인해 주세요"가 붙어도). 어느 값이 맞는지는 비고 `개발 확인:`과 기준 산식 질문으로 처리한다. 본인이 직접 보고 "이상해요"면 오류 수정, 들은 얘기·"~인 듯"·"??"처럼 문제 자체가 확인 안 됐으면 검토 요청.
1. 원인·로직·가능 여부·공수를 개발자에게 묻는다, "공수 보고 결정", 문제 자체가 확인 안 됨 → **검토 요청**. "확인 부탁드려요"는 맺음말일 뿐 신호가 아니다("E/R이 0으로 나와요, 확인 부탁드려요" → 오류 수정).
2. 고장 신호("안 돼요", "에러", "깨져요", "값이 달라요") 또는 **시안·기획·다른 화면의 표기와 다르게 구현됨** → **오류 수정**.
3. **기획 변경**(이전 기획대로 개발됐는데 기획이 바뀜) → **기능 개선**.
4. "~로 바꿔 주세요"인데 원래 정해진 동작인지 모름 → **기능 개선** + [선택] 질문 "원래 정해진 동작인가요?" (모르면: 기능 개선으로 등록).
5. 기존 화면에 필터·컬럼·지표·토글 추가 → **기능 개선**. 새 시안이 있다는 것만으로 신규 기능이 아니다.
6. 새 메뉴·탭·독립 흐름 → **신규 기능**.

1-1에서 팀이 경계 사례를 다르게 분류한 것을 확인했으면 팀 방식을 따른다. 종류는 제목에 넣지 않고 본문 첫 줄 `**이슈 유형:** ...` 한 곳에만 쓴다.

## 3. 제목

**메뉴**: LNB에서 고르는 화면(Social Marketing, GMA, Admin). **탭**: 메뉴 안의 하위 화면(Performance Trend, Performance Detail). **영역**: 화면 안의 부분(Metric Card, 차트, 범례, 툴팁, 테이블, 필터) — 탭 자리에 넣지 않고 이슈 문구에 넣는다.
**탭 판정**: 알려진 탭(Social Marketing의 Performance Trend / Performance Matrix / Performance Detail, 1-1에서 확인한 것)이 입력에 나오거나, 입력에 '탭'이라는 말이 있거나, `>`·`/`로 메뉴와 하위 화면을 나눠 썼거나, 1-1에서 탭임을 확인했을 때만 3단. 그 외에는 2단.

| 상황 | 형식 | 예 |
|---|---|---|
| 탭 있음 | `메뉴 > 탭 > 이슈` | `Social > P.Detail > 엑셀 YoY 미반영` (30자) |
| 탭 없음 | `메뉴 > 이슈` | `GMA > E/R 툴팁 문구 변경` (18자) |
| 말머리 태그 | `[태그] 메뉴 > …` | `[집계 오류] GMA > E/R 카드·표 불일치` (26자) |
| 새 탭·메뉴 | `진입 위치 > 새 이름 탭 신규` | `Methodology > Search 탭 신규` (25자) |
| 메뉴 모름 | `[확인 필요] > 이슈` | `[확인 필요] > 차트 수치 오류` (18자) |
| 여러 메뉴 공통 요소(Chatbot·GNB·LNB)·여러 메뉴 적용 | `공통 > 요소 > 이슈` | `공통 > Chatbot > 답변 표 잘림` (22자) |

- 메뉴·탭 이름은 **화면의 영문 그대로**(번역 금지). 중간 단계(Overview 등)는 생략한다.
- **팀 축약어**: Social(=Social Marketing), P.Detail(=Performance Detail), UNPK, GMA(Global Media Analysis), CMA(Competitive SOS), PDA/PDM(Paid Digital Media Analysis), DPA, SPA. 목록에 없는 축약어는 만들지 않는다(1-1에서 확인한 것만 추가).
- **말머리 태그**(해당될 때만, 1개): `[보안]`(권한·데이터 노출), `[긴급]`(입력에 긴급이 명시됨), `[집계 오류]`(화면 수치 오류), `[엑셀 집계 오류]`(Excel 수치 오류), `[퍼블리싱]`(화면 마크업·스타일 오류). 여럿 해당되면 [보안] > [긴급] > 나머지.
- 후속 티켓은 끝에 `(MX-598 후속)`. 30자를 넘으면 비고 `관련 티켓: MX-598 후속`으로 옮긴다.
- **30자 이내(공백·`>`·태그 포함).** 영문은 한 글자씩 센다. Claude가 `python3 -c "import sys;print(len(sys.argv[1]))" "제목"`으로 세고 `(N자)`를 붙인다.
- 이슈 문구는 명사형: `~오류`, `~불일치`, `~미반영`, `~겹침`, `~추가`, `~변경`, `~통일`, `~제거`, `~신규`, `~검토`. `수정 요청`, `UI 수정`, `버그`, `이슈`, `관련`만으로는 쓰지 않는다.

**30자를 넘으면 (순서대로). 메뉴와 탭은 어떤 단계에서도 빼지 않는다. 메뉴를 모를 때의 `[확인 필요]`도 지우지 않는다.**
① 팀 축약어 사용, Overview 생략 → ② 탭 축약: 팀 패턴(P.Detail)대로 `P.Trend`, `P.Matrix`. 목록에 없는 축약은 본문 위치 줄에 `(제안)`을 붙이고 [선택] 질문으로 확인 → ③ 이슈 문구 압축: 영문·한글 중 짧은 쪽(`전월 대비` → `MoM`, `Channel 필터` → `채널`) → ④ 세부 조건은 본문으로 → ⑤ 말머리 태그를 제목에서 빼고 헤더에 `말머리: [퍼블리싱] (제목에서 뺌)`, 본문 첫 줄에 `**말머리:** [퍼블리싱]`(JIRA 레이블로 지정해도 됨). [보안]·[긴급]은 끝까지 유지 → ⑥ 그래도 넘으면 30자를 지키는 최선안 1개와 원안 1개를 함께 제시한다.

나쁜 예: `[오류 수정] Social 엑셀 오류`(종류 포함·구분자 없음), `Social Marketing > Overview > Performance Detail > Excel 오류`(축약·생략 안 함, 30자 초과), `GMA > 수정 요청`(내용 없음), `GMA > Metric Card > 툴팁 오류`(영역을 탭 자리에).

## 4. 본문

```markdown
**이슈 유형:** 기능 개선

## 요청 배경
- **문제:** (누가, 어떤 상황에서, 무엇이 곤란한지)
- **목적:** (해결되면 좋아지는 것 / 근거: VOC, 요청 법인·부서)

## 요청사항
(5장)

## 검증 항목
- [ ] (조건/행동)하면 (관찰 가능한 결과)가 된다

## 비고
- (필요할 때만)
```

**요청 배경** — 문제는 필수. 오류 수정은 목적 생략 가능, 영향이 입력에 없으면 `- **문제:** (현상 1줄) / 영향 [확인 필요: 영향]`. 다른 종류에서 이유가 없으면 `[확인 필요: 요청 이유]`.

**요청사항** — 굵은 소제목과 번호 목록·표. 한 항목에 한 동작. 화면 문구는 따옴표로 입력 그대로. 시안 링크는 해당 항목 옆에 `[(피그마 시안)](링크)`. "이번엔 안 함"은 `범위 밖`.

**검증 항목** — 직접 해 보고 예/아니오로 판정할 수 있게. 보통 3~6개.
- 요청사항 각 항목이 최소 1개 검증과 연결된다. 오류 수정은 "재현 조건대로 하면 문제가 없다" + "기존처럼 ~된다" 1개 이상.
- 금지: `정상 동작한다`, `잘 보인다`, `시안과 일치한다`(단독), `배포 전과 같다`.
- **판정 가능한 기준 우선**: 수치는 비교 기준을 쓴다(`같은 조건의 Metric Card 값과 같다`). 기대값을 알면 `| 항목 | 기대값 | 실제값 |`(분자·분모 포함), 모르면 [확인 필요]. 긴 텍스트는 "최대 길이로 테스트".
- 미확정 값은 `[확인 필요: 항목]` + `(확정 후 채움)`. "확정된 규칙대로"는 쓰지 않는다.
- 기간은 경계를 쓴다: 시작·종료일 포함, Month/Week, One Month/Period, 기준 시각. 입력에 없으면 [확인 필요].
- 시각 검증은 `대상 + 기준 시안 프레임 + 화면 조건(화면 폭·LNB 펼침/접힘·Chatbot 열림)`. 화면 폭 숫자는 입력·시안에 있을 때만. 디자이너가 볼 항목은 끝에 "— 디자이너 확인".
- 권한: 화면뿐 아니라 URL 직접 입력, API 응답, Excel/PDF 다운로드에서도 막혀야 한다.
- 검토 요청: "답변이 댓글로 남겨졌다"로 쓴다.

**비고** — 첫 줄에 긴급·일정(있을 때만): `**긴급:** 보고서 수치 오류` / `**일정:** 2026-11-02(월)까지`. 보안·권한·외부 보고 수치 오류(또는 그 의심)는 반드시 긴급. 그 밖에 범위 밖("별도 티켓 전달 예정"), 관련 티켓, `개발 확인:`(개발자가 직접 확인할 수 있는 항목). 없으면 섹션째 생략.

## 5. 요청사항 구조

| 종류 | 굵은 소제목 (굵게 = 필수) |
|---|---|
| 오류 수정 | **재현 조건** / **재현 절차** / **실제 결과** / **기대 결과**(근거: 기획서·시안·이전 동작) |
| 검토 요청 | **검토 대상** / **검토 질문**(번호, 예/아니오·선택지로) / **필요한 답변**(원인, 로직, 가능 여부, 공수) |
| 기능 개선 | **위치** / **ASIS / TOBE**(`\| 구분 \| ASIS \| TOBE \|`) / 범위 밖 |
| 신규 기능 | **위치·진입 경로** / **구성 요소** / **동작 흐름**(번호) / 범위 밖 |

**재현 조건** (오류 수정, 버그 유형별로 해당 항목만)

| 유형 | 쓸 것 | [필수]인 경우 |
|---|---|---|
| 집계·기능 (값 틀림, 다운로드 실패, 에러) | 환경(운영계/개발계), 메뉴 경로, 기간, 법인·지역, 지표, 토글(YoY/MoM), 정렬 | 입력만으로 개발자가 재현할 수 없을 때만 |
| 퍼블리싱 (겹침, 잘림, 색, 간격) | 메뉴 경로, 화면 폭, LNB 펼침/접힘, Chatbot 열림, 브라우저, 스크린샷 파일명 | 스크린샷도 화면 조건도 없을 때만 |

**디자인 줄** — 화면에 보이는 것이 바뀌는 티켓에는 항상 한 줄을 둔다.

| 변경 | 표기 |
|---|---|
| 집계·노출 조건·정렬·기본값만 변경 | `**디자인:** 필요 없음 — 화면 구성은 그대로` |
| 문구만 변경 | `**디자인:** 필요 없음 — 문구 길이 변화만 확인` + 줄바꿈·넘침 검증 1개 |
| 시안이 있음 | `**디자인:** [(피그마 시안)](프레임 링크)`. 입력에 "최종·확정"이 있을 때만 `시안 확정` |
| 모름 | `**디자인:** [확인 필요: 시안 유무]` |

**디자인 블록**은 새 요소·레이아웃이 생기거나, 입력에 시안·디자이너 언급이 있거나, 시안과 다르게 구현된 오류일 때만 펼친다: 시안 링크(프레임 단위, 파일 링크만 있으면 `[확인 필요: 프레임 링크]`) / 컴포넌트(기존·신규, 입력에 있을 때) / 디자이너 할 일.

**그 밖의 조건부 블록** (조건에 맞을 때만)
- **적용 범위**: 수치·필터·표가 바뀔 때 → 화면 / Excel / PDF, Month / Week, 적용 탭 목록 중 입력에 있는 것. 모르면 `[확인 필요: Excel·PDF 동일 적용 여부]`.
- **상태별 동작**: 토글(YoY/MoM)·필터 선택·권한처럼 상태에 따라 동작이 바뀔 때 → `| 상태 | 현재 | 변경 후 |`에 입력에 나온 상태를 모두 쓰고, 나머지는 `[확인 필요: 그 외 상태]` 한 행.
- **화면 상태**: 새 화면·요소가 생길 때 → `| 상태 | 표시 내용 | 시안 |`. 요청이 다루는 상태와 **배경에 언급된 상태(에러 등)는 반드시** 포함. 점검용(출력하지 않음): 로딩 / 데이터 없음 / 에러 / 권한 없음 / 선택 0개 / 긴 텍스트 / 화면 폭 변화.
- **문구 표**: 문구가 2개 이상일 때만 `| 구분 | 현재 표시 | 수정 요청 |`.

**시안·스크린샷**: 시안과 텍스트 요청이 다르면 어느 쪽도 고르지 않고 둘 다 적은 뒤 [필수] 질문 1순위. 스크린샷은 붙여넣기로 들어가지 않으므로 `스크린샷: 첨부 'trend_legend.png'`처럼 파일명으로 가리킨다. 개발 위치(파일·행)는 기획자가 준 경우만 "참고용"으로 쓴다.

## 6. 정보 부족과 확인 질문

- 상대 날짜는 기준 날짜(회의·메시지 날짜)가 있으면 절대 날짜로: `2026-10-20(화) (원문: 다음 주 화요일)`. 없으면 [확인 필요].
- **확인 질문**은 기획자용이라 붙여넣을 블록 **밖**에 둔다. 티켓마다 최대 5개. 개발자가 직접 확인할 수 있는 것은 질문으로 만들지 않고 비고 `개발 확인:`에 쓴다.
- 형식: `1. [필수·기획] 질문 (모르면: 기본 처리)`. 담당은 `기획` / `디자인`.
  - **[필수]** = 답이 없으면 개발 착수가 불가능한 것. 등록은 할 수 있지만, 답이 오기 전까지 JIRA 상태를 **'작업 대기'**로 둔다.
  - **[선택]** = 개발 중 댓글로 정해도 되는 것. 기본값으로 진행하는 대안(`모르면: ~로 진행`)은 [선택]에만 쓴다.
  - 모든 질문에 `(모르면: 누가 답할 수 있는지)`. 예: `(모르면: 등록 후 개발 담당자에게 댓글로 확인)`, `(모르면: 디자이너에게 물어 답을 붙여 주세요)`.
  - `(확정 후 채움)`은 기획자가 답을 받은 뒤 JIRA 본문을 직접 수정해 채운다.
- 기획자가 개발 지식 없이 답할 수 있는 말로("재현 절차는?" → "어떤 메뉴에서 어떤 기간·법인을 골랐을 때 생겼나요?").
- 본문의 모든 `[확인 필요]`는 확인 질문, 비고 `개발 확인:`, `(확정 후 채움)` 중 하나와 연결되어야 한다. 질문이 5개를 넘으면 `그 외 N건은 본문 [확인 필요] 참고 (개발 중 협의 가능)`.

**초안 모드** — 필수 칸의 절반 이상이 [확인 필요]이거나, 한 줄짜리 입력에 위치·증상(또는 원하는 결과)이 빠졌으면 전체 티켓 대신: 제목 블록 + `**이슈 유형:**` + 배경 1줄 + 요청 1~3줄 (블록 안) → [필수] 질문 → "답해 주시면 티켓을 완성해 드립니다."

**답을 받은 뒤**: 같은 티켓을 다시 출력하고 바뀐 곳(유형·제목 포함)을 한 줄로 알린다.

---
**티켓화하지 않은 항목** (해당될 때만)

**다음 행동:** [필수]에 답해 주시면 반영해 다시 정리해 드립니다. / [필수]가 없으면 "바로 등록하셔도 됩니다."

- 긴급이면 헤더에 `· 우선순위: Highest (제안)`을 붙인다. 그 외에는 우선순위를 쓰지 않는다.

- 확인 질문이 없으면 그 부분을 생략한다. 블록 밖에 다른 설명을 붙이지 않는다.

## 8. 자체 점검 (하나라도 실패하면 고친다)

- [ ] 이슈 유형이 2장 판단 순서·1-2 표와 맞다. 의심 문제·보안 의심을 빠뜨리지 않았다
- [ ] 제목: 실측 30자 이내(태그 포함), 메뉴·탭·`[확인 필요]`를 빼지 않음, 영문 메뉴명·팀 축약어, 3장 형식·압축 순서대로, 영역을 탭 자리에 넣지 않음
- [ ] 본문: 이슈 유형 / 배경(문제) / 요청사항(필수 소제목) / 검증 항목. 비고는 필요할 때만. 합니다체
- [ ] 화면이 바뀌면 디자인 줄이 있다. 수치·필터 변경이면 적용 범위가 있다. 블록은 조건에 맞는 것만. "없음" 줄과 반복이 없다
- [ ] 검증 항목은 모두 예/아니오로 판정 가능하다. 미확정이면 `(확정 후 채움)`
- [ ] 입력에 없는 수치·이름·산식·시안 상태가 없다. 판단에는 `(제안)`. 상대 날짜는 절대 날짜로
- [ ] **본문의 모든 [확인 필요]가 확인 질문·`개발 확인:`·`(확정 후 채움)` 중 하나와 연결되어 있다**
- [ ] 질문: 5개 이하, [필수]/[선택]·담당·`(모르면: ...)`, 쉬운 말. [필수]는 착수 불가인 것만
- [ ] 용어는 괄호로 풀었다. 표시는 범례의 세 가지만 썼다
- [ ] 확인 질문 외 모든 내용이 붙여넣을 블록 안에 있다. 초안 모드 조건이면 초안 모드로 출력했다
- [ ] JIRA에는 아무것도 쓰지 않았다(조회만)
