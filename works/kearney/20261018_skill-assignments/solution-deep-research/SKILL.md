# Solution Deep Research (6인 역할 리서치 → 인터랙티브 HTML)

회사 또는 솔루션 이름 하나를 받아, **FDE(Forward Deployed Engineer)나 Deployment Strategist가 하루 만에 이해하고 고객·동료에게 설명할 수 있는 수준**의 리서치 리포트를 만든다.
최종 산출물은 탭·필터·도식·퀴즈가 들어간 반응형 단일 HTML 하나다.

독자가 원하는 것은 뉴스 모음이 아니라 "이게 뭐고, 무엇을 어떻게 해주며, 실제로 어디서 어떤 문제를 어떻게 풀었는가"를 **남에게 설명할 수 있는 이해**다. 모든 판단은 이 기준으로 한다.

---

## 1. CONTEXT

- **입력**: 회사명(예 "Palantir") 또는 솔루션명(예 "Palantir AIP", "Snowflake Cortex"). 둘 다 가능.
  - 회사가 들어오면: 회사 개요 + 주력 솔루션 라인업 전체를 다루되, 사례·플레이북은 매출 비중이 큰 핵심 제품 1~3개에 집중한다.
  - 솔루션이 들어오면: 그 솔루션을 중심에 두고, 회사는 맥락으로만 다룬다.
  - 이름이 모호하면(동명 회사, 리브랜딩, 제품군 이름) 가장 유력한 해석을 고르고 `00_scope.md`에 근거를 적는다. 정말 판단이 불가할 때만 사용자에게 한 번 묻는다.
- **기준일**: 시스템 프롬프트의 오늘 날짜. "최신"은 기준일에서 가까운 순서다. 사례는 날짜 내림차순.
- **언어**: 본문은 한국어. 제품명·기능명·고유명사·원문 용어는 영어 그대로 병기한다(예 "온톨로지(Ontology)"). 독자가 공식 문서를 바로 검색할 수 있게 하기 위해서다.
- **사례 = 실명**: 사례는 실제 회사명이 확인된 것만 넣는다. "A 글로벌 제조사" 같은 익명 사례는 별도 표시(`anonymous: true`)하고 실명 사례보다 아래로 내린다.

## 2. 여섯 역할

자세한 행동 지침·산출 형식은 `references/personas.md`에 있다. 루프 시작 전에 반드시 읽는다.

| 역할 | 한 줄 정의 | 핵심 산출물 |
|---|---|---|
| ⚫ 블랙 | 정보 수집가. 공식 문서·101·사례 페이지부터 Reddit, X, Threads, HN, GitHub, 국내 커뮤니티까지 최대한 넓게 | `01_black_raw.md` (출처 태그 포함 원자료) |
| 🔴 레드 | 비평가. 사실·논리·출처 검증. 출처가 약해도 바로 지우지 않고 작성자 영향력·추론의 합리성을 따져 **신뢰도 등급**을 매긴다 | 이슈 목록(critical/major/minor) + 신뢰도 판정 |
| 🔵 블루 | 옹호자. 강점·기회·성공 요인을 찾고 과도한 비관을 바로잡으며 학습 동기를 준다 | 강점·반론·"왜 배울 가치가 있나" |
| ⚪ 실버 | 15~20년차 실무 전문가. 아키텍처, 실제 구축 난이도, 함정, 경쟁 기술과의 차이 | 기술 정확성 검토 + 현장 팁 |
| 🟡 골드 | 리셀러/SI 파트너 영업. 고객이 사는 이유, 가격·계약 구조, 반론 대응, 디스커버리 질문 | 세일즈 관점 보강 |
| ⬜ 화이트 | PM. 통합·조율·최종 편집, 10점 만점 채점, 9.5점 미만이면 다음 라운드 지시 | `dossier.json`, `review_log` |

역할은 연기가 아니라 **검토 관점의 분리**다. 같은 내용을 서로 다른 눈으로 보게 해서 빈틈을 찾는 것이 목적이므로, 각 역할의 출력은 실제로 서로 다른 지적을 담아야 한다. 모두가 "좋습니다"라고 말하는 라운드는 실패한 라운드다.

## 3. TOOLS

| 도구 | 용도 |
|---|---|
| **WebSearch / WebFetch** | 수집. 지연 로드 도구면 ToolSearch로 먼저 로드. 독립적인 검색은 한 턴에 병렬로 보낸다 |
| **Agent (서브에이전트)** | 있으면 블랙 수집을 영역별로 병렬화하고, 레드·블루·실버·골드 검토를 병렬로 돌린다. 없으면 같은 순서로 직접 수행 |
| **Write / Edit** | 작업 파일 저장 |
| `python scripts/render.py` | `dossier.json` → HTML. 디자인을 매번 새로 짜지 말고 이 스크립트를 쓴다(일관된 품질·속도·검증) |
| **Artifact** (있으면) | 완성 HTML 게시. 없으면 SendUserFile 또는 파일 경로 안내 |

스크립트 경로는 이 SKILL.md가 있는 디렉터리 기준이다.

## 4. WORKFLOW

작업 폴더: 현재 작업 디렉터리 아래 `<slug>-research/` (slug는 영문 소문자-하이픈, 예 `palantir-foundry`). 모든 중간 산출물을 여기 남긴다. 루프가 길기 때문에 컨텍스트가 요약되더라도 파일로 이어서 작업할 수 있게 하기 위해서다.

```
<slug>-research/
├── 00_scope.md          # 대상 정의, 해석 근거, 핵심 제품, 조사 범위
├── 01_black_raw.md      # 블랙 원자료 (라운드마다 추가)
├── reviews/round-N/     # red.md, blue.md, silver.md, gold.md, white.md
├── dossier.json         # 화이트가 관리하는 단일 진실 원천
└── <slug>.html          # 최종 렌더링
```

### Step 0 — 범위 확정 (`00_scope.md`)
대상 정의, 회사/솔루션 구분, 핵심 제품 1~3개, 경쟁군, 조사 축을 적는다. 공식 사이트·문서 사이트·고객사례 페이지·학습(101/Academy/Learn) 페이지 URL을 먼저 찾아 적어둔다.

### Step 1 — 블랙 1차 수집
`references/research-playbook.md`의 수집 축과 쿼리 패턴을 따른다. 서브에이전트가 있으면 아래 4개 축을 **한 턴에 병렬로** 띄운다(각 에이전트에 personas.md의 블랙 지침과 해당 축의 쿼리 패턴, 저장 파일 경로를 넘긴다):

1. **공식·학습 자료**: 제품 페이지, 문서, 101/Getting Started/Academy/튜토리얼, 아키텍처 백서, 가격 페이지, 릴리스 노트
2. **적용 사례**: 공식 customer stories, 고객사 발표(컨퍼런스 세션, 엔지니어링 블로그), 언론 보도, 실적 발표·IR 자료에 언급된 고객
3. **커뮤니티·소셜**: Reddit, X, Threads, LinkedIn, Hacker News, Stack Overflow, GitHub(issues/discussions), YouTube, G2/Gartner Peer Insights, 국내(GeekNews, 블라인드, 커리어리, velog, 디스콰이엇 등)
4. **시장·경쟁**: 애널리스트 리포트 요약, 경쟁사 비교, 회사 연혁·재무·조직

수집 목표(하한선, 대상 규모에 따라 조절): 출처 40개 이상, 실명 사례 후보 10개 이상, 커뮤니티 목소리 10개 이상. 사례는 날짜(발표일/보도일)를 반드시 기록한다.

### Step 2 — 화이트 초안 (`dossier.json`)
`references/data-schema.md`의 스키마대로 초안을 만든다. 이 단계에서 이해하기 쉽게 **재구성**하는 것이 화이트의 핵심 일이다:
- 공식 101/문서의 개념을 FDE가 쓰는 말로 번역한다 (용어 → 정의 → 왜 중요한가 → 고객에게는 이렇게 설명).
- 각 사례를 6단 체인(상황 → 문제 → 솔루션 → 접점 → 방식 → 결과)으로 쪼개고, 연결 구조를 `flow`(노드·엣지)로 그린다. 이것이 사례의 "도식"이 된다. 원자료에 이미지가 없어도 이 도식이 생성 이미지 역할을 한다.
- 퀴즈 초안(객관식 4지선다, 12~20문항)을 플레이북·사례에서 출제한다.

### Step 3 — 검토 라운드 (레드·블루·실버·골드)
서브에이전트가 있으면 4개 검토를 **한 턴에 병렬로** 실행한다. 각 검토자에게 `dossier.json` 경로, `01_black_raw.md` 경로, personas.md의 해당 역할 지침, 저장 경로(`reviews/round-N/<role>.md`)를 준다. 검토자는 `dossier.json`을 직접 수정하지 않는다 — 수정은 화이트만 한다(충돌 방지).

각 검토는 personas.md의 형식으로: 이슈마다 `[severity] 위치(JSON 경로) / 문제 / 제안 / 근거`. 추가 수집이 필요하면 `NEED_RESEARCH:`로 표시한다.

### Step 4 — 화이트 통합·채점
1. 네 검토를 읽고 각 이슈에 결정을 내린다: 반영 / 부분 반영 / 기각(이유). 역할 간 의견이 충돌하면(레드 "과장" vs 블루 "타당") 근거를 비교해 조율하고, 결론이 안 나면 양쪽 시각을 모두 본문에 남긴다.
2. `NEED_RESEARCH` 항목은 블랙에게 표적 수집을 시킨다(병렬). 결과를 `01_black_raw.md`에 추가.
3. `dossier.json`을 수정한다.
4. `references/scoring-rubric.md`로 채점한다. 항목별 점수와 **감점 사유를 구체적으로** `reviews/round-N/white.md`와 `dossier.json`의 `review_log`에 남긴다.

### Step 5 — 루프
- **9.5점 이상** → Step 6.
- **9.5점 미만** → 감점 사유를 다음 라운드 과제로 만들어 Step 3(필요 시 Step 1 표적 수집 포함)으로 돌아간다. 두 번째 라운드부터는 변경된 부분과 이전 이슈 해소 여부에 검토를 집중시켜 시간을 아낀다.
- **안전장치**: 최대 5라운드. 5라운드에도 9.5 미만이면, 더 돌려도 오르지 않는 이유(예: 공개 사례 자체가 부족)를 정리하고 현재 버전으로 렌더링한 뒤 사용자에게 남은 갭을 보고한다. 점수를 맞추려고 근거 없는 내용을 채우거나 점수를 부풀리는 것은 금지 — 9.5는 품질의 대리 지표일 뿐이고, 사용자가 실제로 원하는 것은 믿고 설명할 수 있는 리포트다.

채점 공정성: 화이트는 자기 초안을 채점하므로 관대해지기 쉽다. 이를 막기 위해 (a) 루브릭의 체크리스트를 항목별로 기계적으로 확인하고, (b) 해소되지 않은 레드 critical 이슈가 하나라도 있으면 총점 상한 9.0, (c) 서브에이전트가 있으면 최종 라운드 채점은 별도 에이전트(화이트 채점관)에게 루브릭과 파일만 주고 독립 채점시킨 뒤 둘 중 낮은 점수를 쓴다.

### Step 6 — 렌더링·전달
```bash
python <skill-dir>/scripts/render.py <slug>-research/dossier.json -o <slug>-research/<slug>.html
```
- 스크립트는 두 파일을 만든다: `<slug>.html`(브라우저에서 바로 여는 단독 파일)과 `<slug>.artifact.html`(Artifact 게시용 — Artifact는 doctype/head 래퍼를 스스로 붙이기 때문).
- 스크립트가 스키마 검증 경고를 내면 고친 뒤 다시 렌더링한다. 경고는 루브릭 체크리스트와 대응하므로 채점 전에 한 번 돌려보면 감점 요인을 빨리 찾을 수 있다.
- Artifact 도구가 있으면 `<slug>.artifact.html`을 게시한다(아이콘 `"research"`, description은 한 문장 요약). 외부 이미지는 Artifact 보안 정책상 표시되지 않으므로, 사례 이미지는 `image.path`(로컬 파일 → 렌더러가 임베드)로 넣거나 도식으로 대신한다.
- 사례 이미지 파일을 쓰고 싶으면 공식 사례 페이지의 대표 이미지를 내려받기 전에 사용자에게 확인한다. 없다면 `flow` 도식이 사례의 이미지 역할을 한다.
- 사용자에게: 최종 점수와 라운드별 점수 변화, 사례 수, 퀴즈 문항 수, 신뢰도가 낮은 항목 요약, 파일 경로/링크를 짧게 보고한다.

## 5. 품질 기준 (화이트가 항상 염두에 둘 것)

- **설명 가능성**: 각 섹션을 읽은 사람이 화이트보드 앞에서 3분 설명을 할 수 있는가. `brief.elevator_30s`와 `brief.explain_3min`이 그 시험대다.
- **사례의 인과**: "A사가 X를 도입했다"는 뉴스다. "A사는 (상황)에서 (문제)를 겪었고, X의 (기능)을 (기존 시스템/사용자 접점)에 (방식)으로 연결해 (정량 결과)를 얻었다"가 사례다. 6단 체인 중 원자료에 없는 칸은 추정임을 명시(`inferred` 필드)하고, 합리적 추론 근거를 적는다.
- **출처 투명성**: 본문 문장 끝에 `[S3]`처럼 출처 ID를 단다(렌더러가 링크로 바꾼다). 커뮤니티·소셜 출처는 지우지 말고 `tier`와 레드의 신뢰도 판정으로 무게를 표시한다.
- **최신성**: 제품명 변경·기능 폐기·가격 개편을 반영한다. 오래된 정보는 날짜를 붙여 맥락을 준다.
- **퀴즈**: 단순 암기(설립 연도)보다 이해·적용(이 고객 상황에 맞는 모듈은?)을 우선. 오답 선택지도 그럴듯해야 하고, 해설은 왜 정답인지와 오답이 왜 틀렸는지를 함께 설명한다.
  - 정답 위치를 A~D에 고르게 나눈다. 문제를 쓰다 보면 정답을 습관적으로 두 번째 자리에 두게 되는데(테스트에서 22문항 중 20개가 B였다), 그러면 응시자가 내용을 몰라도 패턴으로 맞힌다. 다 쓴 뒤 정답 분포를 세어 보고 선택지 순서를 섞는다. 해설에서 정답을 "B"처럼 글자로 가리키지 말고 내용으로 가리켜야 섞어도 안전하다. `render.py`가 쏠림을 경고한다.
