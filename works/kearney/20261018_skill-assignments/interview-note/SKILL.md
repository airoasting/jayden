# 인터뷰 노트 작성 스킬

컨설팅 보고서 작성을 위해 진행한 현업·전문가 인터뷰를 복기하는 노트를 만든다. 인터뷰에 참석하지 않은 팀원이 노트만 읽고도 내용을 **의미 손실 없이** 이해하고, 보고서에 바로 가져다 쓸 수 있어야 한다. 그래서 인터뷰 진행 순서가 아니라 **유관 주제별로 재구조화**하는 것이 핵심이다.

산출물은 Excel(.xlsx)이며, 복사해 붙이기 쉬운 텍스트(.txt) 버전도 함께 만든다.

## 전체 흐름

```
전사록 읽기 → [Black] 초안 → [Red] 검증 → (지적사항 있으면 Black 재작성, 반복) → [Blue] 최종 검토/용어 해설 → JSON 정리 → Excel 생성
```

Red 루프는 통과 판정이 날 때까지 반복하되 보통 2~3회면 충분하다. 사용자에게는 루프 전체 대화를 길게 보여주지 말고, 마지막에 "Red가 무엇을 잡았고 어떻게 고쳤는지"를 요약해서 알려준다 (Excel의 Review Log 시트에도 남긴다).

## Step 0. 전사록 준비

- 업로드된 파일 내용이 컨텍스트에 이미 있으면 그대로 사용하고, 경로만 있으면 file-reading 스킬 방식으로 읽는다.
- 전사록은 잡음 때문에 오전사가 있다. 깨진 글자나 문맥에 맞지 않는 단어는 **앞뒤 문맥으로 추정해 고쳐서 해석**한다. 다만 추정이 불확실한 부분(특히 숫자, 회사명, 제품명)은 노트 본문에 확신 있는 것처럼 쓰지 말고 `(전사 불명확, "OO"로 추정)`처럼 표기하고 Red 검토 대상으로 넘긴다. 틀린 숫자를 자신 있게 쓰는 것이 가장 큰 사고이기 때문이다.
- 인터뷰 메타 정보(전문가 소속/직책, 일자, 주제)가 있으면 파악해 둔다. 없으면 비워 둔다. 지어내지 않는다.
- 사용자가 기존에 유사한 주제의 인터뷰 노트나 보고서 맥락을 줬다면, 소분류 체계와 용어 통일에 활용한다.

## Step 1. Black — 인터뷰 노트 작성

**페르소나**: 탑티어 전략 컨설턴트. 전사록을 읽고 핵심 정보를 의미 손실 없이 구조적으로 파악할 수 있는 노트를 쓴다.

### 구조화 원칙
1. 시간 순서를 버리고 **주제(chunk)별로** 재분류한다. 인터뷰 후반부에 앞선 주제를 보충한 발언이 있으면 같은 주제 아래로 합친다.
2. 주제 수는 보통 4~10개. 한 주제에 발언이 너무 많으면 쪼개고, 한 줄짜리 주제는 인접 주제에 흡수한다.
3. 구조화 때문에 맥락이 잘리면 안 된다. 전문가가 "그래서/왜냐하면/다만" 식으로 조건과 이유를 달았다면 그 연결을 보존한다. 어느 시장, 어느 시점, 어떤 고객군에 대한 발언인지 같은 전제도 함께 적는다.

### 양식 (정확히 이 형태)

```
[주제]
• (소분류) 시사점을 담은 핵심 메시지 ~함
  - 해당 메시지의 설명·근거·백업 (구체적인 회사명, 숫자, 사례)
  - 추가 디테일
• (소분류) 핵심 메시지 ~임
  - 디테일
```

- `[ ]` : 해당 chunk의 주제. 그 바로 아래에 불렛을 붙여서 쓴다 (주제와 내용 사이에 빈 줄이나 군더더기 설명을 넣지 않는다).
- `( )` : **단어 형태의 소분류** (예: 가격, 경쟁구도, 리드타임, 규제). 길게 쓰지 않는다. 한 주제 안에서 소분류는 겹치지 않게 한다.
- 불렛(•) : 전문가가 답변한 **주요 메시지**. 단순 사실 요약이 아니라 **시사점을 뽑을 수 있는 의미를 담은 메시지** 형태로 쓰고, **전문가가 쓴 워딩을 최대한 살린다.** 문장은 "~함", "~임" 같은 보고서체(개조식)로 끝낸다.
- 서브 불렛(-) : 그 메시지에 대한 설명, 근거, 백업. 계위가 더 내려가는 내용은 별도 기호를 늘리지 말고 서브 불렛 안에서 디테일하게 풀어 쓴다.

### 좋은 불렛 vs 나쁜 불렛
- 나쁨: `• (가격) 가격이 오름` → 사실만 있고 시사점·워딩이 없음
- 좋음: `• (가격) 2Q부터 현물가가 계약가를 역전해 "사는 쪽이 협상력을 잃은 국면"이라고 진단함` + 서브 불렛에 수치/사례

### 정확성 규칙 (가드레일)
- **숫자와 기업명은 하나도 틀리거나 빠지지 않게** 옮긴다. 단위(억/조, %, %p, USD/KRW), 기간(YoY/QoQ, 연도), 범위("20~30%")까지 그대로 보존한다.
- 전문가의 말이 상식이나 리서치와 달라 보여도 **전문가의 워딩을 그대로 쓴다.** 고치지 않는다. 의심이 가면 해당 불렛에 검증 플래그만 붙인다 (Step 2 참고).
- 전문가가 **앞에서 한 말을 번복**했거나 서로 모순되는 수치를 말했다면 두 발언을 모두 적고 `[번복]` 플래그를 붙여 짚는다.
- 추측, 일반 상식, 본인 의견을 전문가 발언처럼 섞지 않는다. 전문가가 말하지 않은 내용은 노트에 넣지 않는다 (해설은 Blue의 몫이고 별도 칸에 들어간다).
- 전문가의 개인 의견/추정과 확인된 사실이 구분되도록, "~로 봄", "~로 추정함", "~라고 언급함" 등으로 확신 수준을 반영한다.

### Key takeaway
상세 노트가 끝나면 핵심 내용을 종합한 **시사점 4~5개** 이내를 불렛 문장(~함/~임)으로 쓴다. 주제별 요약의 반복이 아니라, "그래서 우리 보고서에 어떤 의미인가"가 드러나야 한다. 숫자와 기업명이 필요한 곳에서는 포함한다.

## Step 2. Red — 비판적 검토

**페르소나**: 까칠한 Project Manager / Partner. 대충 넘어가지 않는다. Black의 초안을 아래 항목으로 검토하고, 지적사항을 목록으로 만들어 Black에게 돌려보낸다.

### A. 사실 검증
- **전사록 대조**: 노트의 숫자, 회사명, 날짜, 고유명사가 전사록 원문과 일치하는지 한 줄씩 확인한다. 누락된 숫자/회사명도 잡는다.
- **리서치 대조**: web_search 등 검색 도구가 있으면 핵심 수치, 기업명 표기, 제품/기술 명칭, 시장 consensus를 실제로 조회해 확인한다. 도구가 없으면 알고 있는 범위에서 검토하되, 확인하지 못한 것을 확인한 것처럼 말하지 않는다. 시점에 민감한 정보(최근 실적, 가격, 규제)는 검색을 우선한다.
- **전문가 발언이 consensus와 어긋날 때**: 노트의 본문은 전문가 워딩 그대로 두고, 해당 불렛 옆에 검증 플래그(`[검증필요]`)와 함께 "무엇이 어떻게 다른지, 근거 출처"를 Black이 적도록 요청한다. 틀렸다고 단정하지 말고 "리서치상 다르게 확인됨" 수준으로 쓴다.
- **번복/모순**: 전문가가 앞뒤로 말을 바꿨거나 수치가 서로 안 맞는지 확인하고 `[번복]`으로 짚게 한다.
- **애매한 표현**: 읽는 사람이 의미를 두 가지 이상으로 해석할 수 있는 문장(주어 불명, 지시어, 기준 시점 누락, 비교 대상 불명)은 명확히 하도록 요구한다.
- **오전사 보정이 적절했는지**: Black이 추정으로 고친 부분이 문맥상 합당한지 확인한다.

### B. 구조 검토
- 같은 주제가 두 chunk에 흩어져 있지 않은가? 진행 순서대로 쓴 흔적은 없는가?
- 소분류 `( )`가 단어 형태이고 서로 겹치지 않는가?
- 불렛이 사실 나열이 아니라 시사점을 가진 메시지인가? 서브 불렛에 있어야 할 근거가 불렛에 올라와 있거나 그 반대는 아닌가?
- 구조화하다가 맥락(조건, 이유, 전제, 대상 시장/시점)이 잘려나간 곳은 없는가?
- 보고서체(~함/~임)가 일관적인가? 형식이 요청한 양식과 정확히 맞는가?
- Key takeaway가 4~5개 이내이고 종합적 시사점인가?

### 출력 형식
지적사항을 번호 목록으로 낸다. 각 항목에 **위치(주제/소분류), 문제 유형(사실/누락/모호/구조/번복/consensus), 요구하는 수정**을 적는다. 문제가 없으면 "PASS"를 선언한다. 가볍게 PASS하지 않는다. 숫자 대조를 실제로 했다는 확신이 있을 때만 통과시킨다.

Black은 지적을 받아 노트를 수정하고 Red가 다시 확인한다. 모든 지적이 해소되면 Step 3으로 넘어간다.

## Step 3. Blue — 산업 전문가 검토

**페르소나**: 해당 산업에서 활동하는 또 다른 전문가. 인터뷰 전문가와 같은 업계 사람의 눈으로 본다.

1. **밸류 평가**: 각 주제/메시지가 보고서에 쓸 만한 가치가 있는지 본다. 인터뷰 노트에 `★` 같은 마킹을 본문에 섞지 말고, Review Log 시트에 "보고서 활용 가치 높음/중간/참고" 정도로 코멘트한다. 핵심이 빠졌거나 과대평가된 메시지가 있으면 짚는다.
2. **용어 해설**: 인터뷰에 참여하지 않았고 업계 경험이 없는 독자가 막힐 만한 개념(industry-specific 용어, 약어, 제품/기술명, 관행)을 골라 쉽게 풀어서 설명한다. 한두 문장, 노트 안에서 나온 맥락에 맞게 설명한다. 해설은 **본문과 분리된 Glossary**에 넣는다. 전문가 발언과 Blue의 해설이 섞이면 안 된다.
3. **업계 관점의 맥락 보충**: 본문에는 없지만 이해에 필요한 배경이 있으면 Review Log에 남긴다. 본문의 전문가 워딩은 건드리지 않는다.
4. Blue가 본문 내용의 오류(사실 관계)를 발견하면 직접 고치지 않고 Red 방식의 플래그(`[검증필요]`)로 남긴다.

## Step 4. 산출물 생성

최종 노트를 아래 JSON으로 정리해 `scripts/build_excel.py`로 Excel과 텍스트를 만든다.

```bash
python scripts/build_excel.py note.json /mnt/user-data/outputs/인터뷰노트_<주제>.xlsx
# 같은 위치에 .txt 도 함께 생성됨
```

JSON 스키마:

```json
{
  "title": "인터뷰 제목/주제",
  "meta": {"전문가": "OO사 전 부사장", "일자": "2026-10-10", "인터뷰 주제": "..."},
  "topics": [
    {
      "topic": "주제명",
      "items": [
        {
          "label": "소분류(단어)",
          "message": "시사점을 담은 핵심 메시지 ~함",
          "details": ["설명/근거 ~함", "추가 디테일 ~함"],
          "flags": [
            {"type": "검증필요", "text": "리서치상 OO로 확인됨 (출처: ...)"},
            {"type": "번복", "text": "앞서 X라고 했으나 후반부에 Y라고 말함"}
          ]
        }
      ]
    }
  ],
  "takeaways": ["시사점 1 ~함", "시사점 2 ~임"],
  "glossary": [{"term": "용어", "explanation": "쉬운 설명"}],
  "review_log": [
    {"reviewer": "Red", "location": "주제 > 소분류", "type": "사실", "comment": "지적 내용", "resolution": "수정 내용"},
    {"reviewer": "Blue", "location": "주제 전체", "type": "밸류", "comment": "보고서 활용 가치 코멘트", "resolution": ""}
  ]
}
```

`flags`와 `glossary`, `review_log`는 해당 사항이 없으면 빈 배열 또는 생략한다. Excel은 아래 시트로 구성된다.

| 시트 | 내용 |
|---|---|
| Interview Note | 주제 / 소분류 / 핵심 메시지 / 상세 설명 / 검증 코멘트 |
| Key Takeaway | 시사점 4~5개 |
| Glossary | Blue의 용어 해설 |
| Review Log | Red·Blue 검토 내역과 반영 결과 |

## Step 5. 사용자에게 전달

- `present_files`로 .xlsx(와 .txt)를 공유한다.
- 채팅에는 짧게: 주제 chunk 개수, Key takeaway 요약 1~2줄, **Red가 잡은 주요 이슈** (특히 `[검증필요]`, `[번복]`, 전사 불명확 추정 항목)만 알려준다. 전체 노트를 채팅에 다시 붙여넣지 않는다.
- 사용자가 확인해야 할 불확실한 부분(추정으로 고친 숫자/회사명)은 반드시 명시한다.

참고 예시는 `references/example.md`를 본다.
